# Data Dictionary — Phase 4 (Dataset Preparation)

## 0. Everything here is simulated

**No real KLE Tech student, application, or payment record exists anywhere in this project.**
Every row in every file under `ml/data/` was generated by `ml/simulate.py` from the assumptions in
`ml/config.py`. Where a number below looks specific (a fee, an eligibility rule, a processing
capacity), it is either copied from the placeholder policy already in the running app
(`backend/app/services/eligibility.py`, `payments.py` — Phase 3) or an assumption made for this
phase and labelled as such. None of it should be read as a claim about the real KLE Tech
population, workload, or policy.

**Public benchmark dataset:** the project brief names a public Kaggle payment/transaction dataset
as optional. This sandbox's network egress does not allow reaching `kaggle.com` (confirmed:
`curl` returns `403 Host not in allowlist`, i.e. a proxy block, not a Kaggle-side error) — so no
public dataset is included in this checkpoint. See §6 for what a team member with unrestricted
network access should do instead of just merging it in.

## 1. How the data is generated (`ml/simulate.py`)

The simulator does not draw student/application/payment rows independently — it plays the real
Phase 3 workflow forward in simulated time, so the relationships between tables are the same ones
the running app would produce:

```
students exist for years  →  applications arrive (seasonal)  →  OCR runs  →  rule-based
eligibility (Phase 3 rules)  →  payment (fee schedule, retries)  →  FIFO admin queue with finite
daily capacity  →  some applications are held for manual review (latent risk model)  →  decision
(VERIFIED / REJECTED)
```

Turnaround time is never assigned directly — it **emerges** from a queue simulation with realistic
seasonal load, weekends/holidays, and staff-leave windows, the same way it would in the real
system. Anomalies (duplicate requests, payment retries, frequency bursts, amount mismatches) are
injected at known rates alongside benign look-alikes (legitimate multi-document alumni requests,
honest re-applications after a rejection, single accidental payment retries) specifically so the
anomaly-detection problem in Phase 5C isn't trivially easy.

Run with `python -m ml.make_datasets` from the project root. Same seed (`ml/config.py: SEED`) →
byte-identical CSV files (checked by a test, see §7).

## 2. Files

```
ml/data/
├── raw/
│   ├── students.csv               one row per simulated student
│   ├── applications.csv           one row per application (workflow state at the snapshot date)
│   └── transactions.csv           one row per payment ATTEMPT
├── labels/
│   ├── application_labels.csv     answer key: did this application need manual review?
│   └── transaction_labels.csv     answer key: is this payment attempt anomalous, and how?
├── processed/                     model-ready datasets, one per Phase 5 component
│   ├── forecast_daily.csv         Phase 5A: daily demand + turnaround time, one row per (date, document type)
│   ├── tat_applications.csv       Phase 5A (alternative grain): one row per VERIFIED application
│   ├── risk_scoring.csv           Phase 5B: one row per decided, eligible application
│   └── anomaly_transactions.csv   Phase 5C: one row per payment attempt
└── dataset_summary.json           generation config, checksums, and the sanity numbers in §5
```

**Raw vs. processed vs. labels:** `raw/` is what the running app's database would actually contain.
`processed/` is engineered from `raw/` purely with `pandas` (see `ml/prepare.py`) — Phase 5 should
read `processed/`, not reinvent this feature engineering. `labels/` is the answer key, produced by
the simulator alongside `raw/` — it is **never** merged into a model's feature columns; every
column that comes from it in a processed file is prefixed `label_`.

## 3. `raw/students.csv`

| Column | Type | Meaning |
|---|---|---|
| `student_id` | int | Surrogate key. |
| `usn` | str | Simulated USN in the portal's `01FE{YY}{BRANCH}{NNN}` format. |
| `department` | str | One of the 5 departments in `backend/app/db/seed_students.py`. |
| `admission_year`, `graduation_year` | int | `graduation_year = admission_year + 4`. |

A student's semester, CGPA, backlog count, and fee status are **not** stored here — they are a
function of *when* an application was submitted (a student's CGPA in year 2 differs from year 4).
Each application carries its own `..._at_submission` snapshot instead (§4); see
`ml/simulate.py:_state()`.

## 4. `raw/applications.csv`

| Column | Meaning |
|---|---|
| `application_id`, `student_id`, `document_type` | Keys. |
| `submitted_at` | When the application was filed. |
| `semester_at_submission`, `is_alumni`, `cgpa_at_submission`, `backlog_count_at_submission`, `fee_status_at_submission`, `past_fee_delays_12m` | The student's academic/fee snapshot **at that moment** (`past_fee_delays_12m` = how many of the preceding 12 months had fee status DUE). |
| `num_documents` | How many files were attached (0 = none uploaded). |
| `ocr_status` | `NONE` (no files) / `SUCCESS` / `FAILED`, mirroring Phase 3's `ocr_results.status`. |
| `ocr_detected_cgpa` | The CGPA OCR "read" off the document; usually equal to `cgpa_at_submission`, sometimes off by a simulated OCR error, `NaN` if OCR failed or found nothing. |
| `eligibility_result` | `ELIGIBLE` / `NOT_ELIGIBLE`, computed by **the exact same rule** as `backend/app/services/eligibility.py` (checked by a validator test — see §7). |
| `status` | Workflow status at the snapshot date: `NOT_ELIGIBLE`, `ELIGIBLE` (rare — see note below), `PAYMENT_PENDING`, `UNDER_REVIEW`, `VERIFIED`, `REJECTED`. |
| `decided_at` | When a `VERIFIED`/`REJECTED` decision was made; `NaT` otherwise. |

**Why some rows are `ELIGIBLE` with no payment at all:** an application submitted right before the
snapshot date can have its (simulated) payment fall after the snapshot and never get recorded —
correct right-censoring, not a bug. It's rare (1 row in the reference run).

**Not eligible → never has a transaction row.** This is asserted by the validator (§7): eligibility
gates payment in the app, so it must in the data too.

## 5. `raw/transactions.csv` and the answer keys

`transactions.csv`: `transaction_id`, `application_id`, `amount`, `payment_status`
(`PENDING`/`SUCCESS`/`FAILED`), `transacted_at`. One application can have several rows (retries).

`labels/application_labels.csv`: `application_id`, `needs_manual_review` (0/1, `NaN` for
`NOT_ELIGIBLE` applications — the question doesn't apply to them), `sim_true_review_probability`
(the **true** generating probability, for validation only — see §7's oracle AUC), `sim_anomaly_type`
(which injected pattern this application belongs to, `NONE` for ordinary ones).

`labels/transaction_labels.csv`: `transaction_id`, `is_anomaly` (0/1), `anomaly_type` (`NONE`,
`AMOUNT_MISMATCH`, `RAPID_RETRIES`, `DUPLICATE_REQUEST`, `FREQUENCY_BURST`).

**These two files are the entire "ground truth" of the exercise.** A model that ever sees
`sim_true_review_probability`, `sim_anomaly_type`, or the raw `application_labels`/
`transaction_labels` files as an input feature has leaked the answer.

## 6. The three Phase-5 datasets (`processed/`)

### 6a. `forecast_daily.csv` — Phase 5A (demand), grain: one row per (date, document_type)
Target: `applications_submitted` (that day's count). A second target, `mean_tat_hours`, is included
for a document type/day but is `NaN` whenever `tat_censored = 1` (some of that day's applications
were still awaiting a decision at the snapshot — averaging only the fast ones would bias the
number low; excluded rather than filled).
Features: calendar (`dow`, `month`, `is_holiday`, `is_working_day`, `academic_phase`,
`week_of_year`, `days_since_start`), `queue_open_at_day_start` (admin backlog at the start of that
day), and `lag_1/7/14/364` + `roll_mean_7/28` of `applications_submitted` **per document type**.
The first 28 days of the simulated period are dropped (not enough history for the rolling
features); `lag_364` is `NaN` for the first simulated year — expected, not a data-quality issue.

### 6b. `tat_applications.csv` — Phase 5A (turnaround time), grain: one row per VERIFIED application
Target: `tat_hours` (`decided_at - submitted_at`). Only `VERIFIED` applications are included
(`REJECTED` ones went through a different, undocumented-length path in the real workflow; mixing
them in would bias a TAT model). Features are everything knowable **at submission time only**:
`document_type`, `num_documents`, `is_alumni`, calendar features of `submitted_at`,
`queue_open_at_submission`, and the applicant's own recent volume (`apps_prev_24h`, `apps_prev_7d`,
`doc_apps_prev_7d`).

### 6c. `risk_scoring.csv` — Phase 5B, grain: one row per **decided** (`VERIFIED`/`REJECTED`),
**eligible** application
Target: `label_needs_manual_review`. Restricted to decided applications because the label is only
observable once an application has been handled — a still-`UNDER_REVIEW` row is right-censored and
excluded, exactly as it would be if you trained this from the live database today. Features:
`cgpa`, `backlog_count`, `department`, `semester`, `is_alumni`, `past_fee_delays_12m`,
`prior_apps_count` and `prior_review_count_lagged` (the student's own history, computed causally —
see §7), `num_documents`, `ocr_failed`, `ocr_cgpa_found`, `ocr_cgpa_mismatch`. `fee_status` is
**not** a feature: once an application is eligible, fee status is always `CLEAR` by construction
(it's a constant column here — the validator would reject it as a constant feature, which is
exactly the point: it belongs to rule-based eligibility, not risk scoring, per the brief's
eligibility/risk-scoring distinction).

**Prevalence and ceiling:** ~18–29% of decided applications need review, by split (see
`dataset_summary.json: risk_scoring.per_split`) — imbalanced but not extreme; don't optimize for
plain accuracy in Phase 5B. **Oracle AUC** (the AUC of the *true* generating probability against
the sampled label) is ~0.83–0.85: this is the ceiling *any* model can reach on this label, because
the label itself has irreducible randomness by design (so Phase 5B should not expect, or chase,
AUC 1.0). A throwaway logistic-regression check (not the real model — that's Phase 5B's job) gets
~0.815 test AUC, so there's real, learnable signal without any one feature trivially solving it (no
single feature exceeds ~0.70 AUC alone).

### 6d. `anomaly_transactions.csv` — Phase 5C, grain: one row per payment **attempt**
Target: `label_is_anomaly` / `label_anomaly_type`. Features are what would be known **at the moment
of that attempt**: `amount`, `expected_amount`, `amount_ratio`, `attempt_index`,
`failed_attempts_before`, `seconds_since_prev_attempt`, `minutes_since_submission`, the student's
recent activity (`student_txns_prior_24h`, `student_other_apps_24h`, `student_other_apps_7d`,
`same_doc_other_apps_7d`, `same_doc_other_paid_apps_7d`), `hour`, `dow`. `payment_status` (this
attempt's own outcome) is included as a feature — it is information about *this* attempt, not a
leak of the future.

**Overall anomaly rate ≈ 2.6%** (all four injected types present; see `dataset_summary.json`).
Each type is well-separated from normal rows by *some* feature (best single-feature AUC 0.91–1.0 —
see §7 for why `AMOUNT_MISMATCH` hits ~1.0, and it's not a leak). **Known, documented limitation:**
about 1 in 6 `RAPID_RETRIES` rows is the *first* attempt of the burst, which looks identical to a
normal first attempt at the row level (nothing distinguishes it until the next attempt happens
seconds later) — a row-level model fundamentally cannot flag it in isolation. If Phase 5C needs to
catch these too, it will need to look at attempts *after* the fact / in short time windows, not at
each row alone; this is worth raising with the team before Phase 5C starts, not something to solve
by inventing a feature that doesn't exist yet.

## 7. How this was validated (`ml/validate_datasets.py`, `ml/tests/`)

Every claim above is checked by code, not just asserted:
- **Referential integrity:** every foreign key resolves; every id is unique.
- **Consistency with the live app:** `eligibility_result` is recomputed independently from the raw
  columns using the *same rule* as `backend/app/services/eligibility.py` and compared row for row;
  payment amounts match `FEE_BY_DOCUMENT_TYPE` from `backend/app/services/payments.py` except on
  rows explicitly labelled `AMOUNT_MISMATCH`.
- **No time travel:** nothing is timestamped after the snapshot date; every processed dataset's
  `train`/`valid`/`test` split is chronological (never shuffled across the boundary).
- **No leakage:** every processed feature column is checked against a banned-substrings list
  (`sim_`, `true_`, `oracle`, `decided`, the exact name `status`, etc.); the risk-scoring history
  features (`prior_apps_count`, `prior_review_count_lagged`) are independently recomputed and
  compared to what shipped, to catch an off-by-one that would leak the future into the past.
- **Signal sanity:** oracle AUC, a throwaway logistic-regression AUC, single-feature AUCs (none
  should trivially solve the problem), and the anomaly separability numbers above are all computed
  and asserted to fall in a plausible range — not just eyeballed once and left alone.
- **`ml/tests/test_pipeline.py`** (`pytest`) re-runs the whole thing twice on a small, fast
  configuration and asserts the output is byte-identical (determinism), plus runs the validator and
  requires zero failures.

## 8. Assumptions worth a second opinion before Phase 5

These are modelling choices, not measurements — flag any that should change:
- Demand seasonality (`SEASON` in `config.py`) assumes exam-season/semester-end spikes per
  document type; picked by intuition about what an academic calendar looks like, not from any real
  KLE Tech record.
- Admin capacity (`CAPACITY_MEAN/SD`, leave windows) is invented to produce a plausible, moderately
  loaded queue (median TAT ≈ 24h, tail past 95h) — tune `config.py` if the team wants a
  faster/slower baseline system.
- The eligibility rules and fee schedule are the Phase 3 placeholders, explicitly not real
  institutional policy (see Phase 3's own status file).
- The manual-review latent model (`RISK_INTERCEPT` and feature weights in `simulate.py`) is
  invented to produce ~20% prevalence and a non-trivial but not-impossible oracle AUC; the specific
  weights (e.g. "past fee delays matter more than CGPA") are a plausible story, not a fact about
  KLE Tech students.
